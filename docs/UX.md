## Current implementation

- **GPU preview failures:** the preview retains its last good GPU image during producer contention and waits for an actual first publication before drawing a new source. A failed shared-texture import, including a different-GPU mismatch, reports Preview unavailable while the rest of the interface remains usable and capture continues. Preview failure is separate from recording failure. This does not provide cross-adapter sharing or migrate the capture GPU.
- **Screen-tool failures:** acquisition, pinning and screen-origin clipboard follow-up failures restore Tools → Utilities with bounded actual error details. Successful color/pin operations and cancelled selections stay on the desktop; later unrelated utility errors do not change navigation. This follows the visible outcome/cancellation distinction in the official [ShareX region guide](https://getsharex.com/docs/region-capture) and [Flameshot troubleshooting guidance](https://flameshot.org/docs/guide/troubleshooting/).
- **Following playback:** the timeline's visible Follow on/off control keeps the playing position inside a zoomed time window. It pages at the edge rather than recentering every frame. Deliberate timeline pan/zoom suspends following; enabling Follow reveals the position immediately, and Fit restores it. This display preference never edits the project or changes playback position. Enter/Space activate the focused control.
- **Capture:** the home page distinguishes off, starting, replay ready, recording and finishing. Replay buffer fill and the active session profile accompany the preview. Starting a full recording from replay explicitly warns that the buffer restarts. A saved replay notice offers Edit and Show in folder for the completed file. Recent captures lead into the shared open action. Settings changed during capture apply to the next capture session.
- **Display interruption and stopping:** Desktop Duplication access loss exposes reconnecting/reconnected notices and retries for up to five seconds on the original GPU/output, with unchanged SDR geometry and supported rotation. Recovery requests a new keyframe. Device removal/reset, HDR, changed dimensions or expiry stop capture explicitly rather than switching targets. Stop and terminal errors attempt both encoder and audio drains, then join the disk writer; failures remain reported even if the other stream can finish. These source paths do not establish real display-mode/session-change recovery; that transition proof remains pending.
- **Application audio:** Capture and Settings offer a shared source dropdown for Desktop audio or a running application, with microphone capture independent. The picker searches accessible application windows; its selected PID and creation-time fingerprint remain in memory only, and RCR restarts with Desktop audio selected. Source choices cannot change during active capture. The selected application includes its children, so the picker asks for the running app rather than a launcher and requires reselection after relaunch. A reused PID fails its fingerprint check rather than capturing another application. Activation failure and target exit are explicit; neither substitutes desktop audio. Application tracks retain their executable label through quick-editor import, including names containing mic/game/system.
- **Audio devices:** Capture and Settings offer saved microphone and desktop-output device choices, including an explicit Windows default. The desktop-output choice selects the endpoint whose sound is captured; it does not change Windows playback routing and does not constrain application capture. Background discovery returns bounded plain device data without activating streams. Pickers support search, keyboard navigation and refresh; unavailable saved choices retain their cached label, while duplicate names remain separate exact-ID choices. Source/device changes are disabled during capture, and late selections cannot modify an active session. Explicit devices must be active and have the correct input/output direction at startup; failure does not substitute a different device.
- **Tray:** a disabled status row and tooltip accompany distinct off/starting/replay/recording/finishing icon states. Recording is not reported until the first encoded frame; cancellation remains available during startup. Enable/Disable instant replay is separate from Save replay. Save is unavailable until encoded frames exist and while finishing; replay cannot be disabled during a full recording. The save label reports available whole seconds. Library and Settings restore the main window to the requested page. Existing screenshot tools and utilities remain available. Visible shortcut hints follow the six configured global bindings; the tray does not register duplicate accelerators. Equal visible state performs no native tray work.
- **Library:** local captures have type filters, text search, favorites, sort controls, thumbnails and grid/list presentation. Captures can receive a display name stored in preferences without renaming the media or project sidecars. Card keyboard handling supports navigation and selection, while search and rename input retain text-editing keys. The rename dialog contains Tab navigation and restores capture focus after dismissal. Discovery, metadata checks and initial newest-first ordering run on a worker; only the latest requested scan can replace the catalog. Existing cards stay visible while refreshing, and the initial scan shows a loading state. An unavailable capture folder retains catalog membership and last-known names, dates and sizes while explicitly marking sources unavailable. Retry and folder controls remain visible; folder preparation runs on one admitted worker. Thumbnail caching is disposable and bounded.
- **Library view persistence:** List/Grid changes apply immediately while one settings worker coalesces pending layout choices. A compact status reports saving or failure; a completed atomic replacement acknowledges the current choice, and a live-worker write failure offers retry. Every `preferences.json` save shares that storage owner, so older synchronous snapshots cannot overwrite a newer layout choice. Other preference changes—including folder, GPU preview, shortcuts and Library import/removal references—still wait synchronously for their existing save/rollback boundary; this is not a general removal of settings stalls. After the UI exits, shutdown allows already admitted writes up to two seconds without retrying failed work. The acknowledgement does not promise survival of power loss. The saving/failed snapshot routes seed presentation state only; native visual results are recorded separately in VALIDATION.md.
- **Batch selection:** Ctrl+click toggles a card and Shift+click adds the inclusive range on the current page, including when using the selection checkbox. Ordinary card activation still opens the capture. The anchor is an exact source path and resets when the page/order/filter changes; existing off-page selections remain selected. This follows [Medal's documented range selection](https://support.medal.tv/support/solutions/articles/48001164598-how-to-manage-clips-on-medal) and the batch-management emphasis in [SteelSeries' gallery redesign](https://techblog.steelseries.com/2023/04/18/GG-notes-36.0.0.html). Native modifier-click and keyboard selection checks have passed; the validation log records their owned-fixture scope.
- **History:** search runs against the complete history database, with 50 results per page, counts and Previous/Next controls. Typing debounces for 150 ms; only the latest requested result can replace the page. Its separate bounded worker does not use capture/upload admission or replace the unfiltered recent-history feed used by Library discovery. Rows do not load unused thumbnail blobs. This corrects the old silent latest-100 search boundary, informed by [ShareX's history search and virtual population changes](https://getsharex.com/changelog). The header, search and pager stay fixed while compact rows scroll. Ctrl+F focuses search, F5 refreshes, and returning after a new capture refreshes stale results. Row focus scrolls into view only when focus changes, preserving manual scrolling. Native database/input checks passed independently of network uploading; see the validation log.
- **Import and removal:** dropped files and Import add references to videos/images/image projects while leaving originals in place. Offline imported paths remain visible and removable as references. Local managed files use reversible Trash; external/offline imported references use unlinking from Library, retaining source bytes, names, favorites and edit sidecars. Undo removal lasts until RCR closes and keeps unfinished work after a partial failure. The Add clip picker uses up to 64 recent named Library choices plus Browse videos; accepting or cancelling a popup restores editor focus.
- **Durable Trash recovery:** Library's Trash browser scans/restores on workers, supports keyboard navigation and displays conflicts and warning details. Managed removals journal original/Trash path pairs before moving files, so journaled files remain restorable after restart. Restore never replaces an existing original; conflicting files and corrupt/unsafe journals stay intact. Recovery journals remain after restoration. Open folder provides manual access to older unjournaled files. External reference unlinking has no durable Trash journal. Scans inspect up to 256 journals and list 2,048 files, ordered by newest journal within at most 4,096 discovered directory items; newer batches outside that subset can be omitted. Byte/move bounds and truncation are reported, with no automatic deletion.
- **Screenshot annotation:** capture-time editing stays over the frozen desktop. Selection, move/resize, undo/redo, contextual annotation properties and copy/save are exposed there. F6 switches between canvas and toolbar focus. Canvas Tab selects the region tool; toolbar Tab/Shift+Tab traverse controls, and Enter/Space activate the focused control without also copying or expanding the canvas selection. The standalone image editor remains available for opened files. Completed worker previews/events wake the UI directly. Large effect previews can reduce raster density with a visible notice while logical zoom, hit testing and annotation coordinates stay unchanged. This preview safeguard does not reduce saved/copied image resolution. Overlay guides are presentation only and do not become exported pixels.
- **Quick video editing:** opening a capture uses the shared Library-to-editor route. The editor exposes linked trimming, split/delete, undo/redo, playback, frame/second stepping, timeline zoom/fit and export. Trim handles keep the grabbed edge at its released timeline position; a trimmed start stays there after release. Trims, deletes and speed changes preserve other pieces' timeline positions. Blank gaps remain until the user closes them by dragging a piece's body. Body dragging freely positions only the selected piece and its linked audio/video group; it does not automatically reorder or pack the strip. Speed changes retain the selected piece's start while changing its duration. The core's explicit `QuickEdit::Reorder` operation still packs pieces for API callers; the UI body drag does not invoke it. Up to eight inactive sessions retain full Undo/Redo history and linked-edit mode in memory; disk saves continue to contain the project only. Reset edits restores the opened source as one undoable operation. Damaged saved edits expose Open original with a recovery backup. Scrubbing prepares a bounded reusable preview for eligible sources while retaining the existing fallback; its persistent cache validates source identity and completed outputs before reuse. Measured scope and limits are recorded in [VALIDATION.md](VALIDATION.md); broader project eligibility is not inferred from this UX revision.
- **Export failures:** a short export notice offers Show details for the bounded actual error chain, without guessing that every failure is a disk-space problem. The details panel wraps/scrolls text, supports Copy details, traps Tab between controls and closes with Escape while restoring focus. This state is separate from autosave and media errors. Each render uses its own adjacent `.rcr-export-*` directory; after FFmpeg starts, failed/cancelled renders retain any partial output with Show in folder for inspection or cleanup. Empty staging directories are removed. Successful publication does not overwrite another destination, and cancellation before publication leaves no completed export.
- **Source recovery:** opening saved edits or cached history validates source metadata on the media worker before displaying or autosaving the restored state. New assets carry canonical-path/size/modification-time stamps; legacy assets require compatible probed duration, dimensions and stream indices/kinds. Validation covers Undo/Redo snapshots, and only a completely successful check adopts legacy stamps. A changed or unavailable source preserves the prior edits and offers recovery rather than silently applying old metadata to replacement media. Open original keeps recovery copies of disk edits and the latest unsaved project before loading fresh metadata from the current file; it cannot restore old source bytes. Offline Windows paths can still locate existing sidecars across ordinary/verbatim path spelling. Export rejects detected changes before output creation. Stamps are conservative metadata checks, not cryptographic content identity or continuous source monitoring.
- **Autosave feedback:** Saving… means the current edits are queued or awaiting the save worker. Saved appears only after a successful acknowledgement for the latest revision. A stale acknowledgement cannot make newer edits appear saved. Failed snapshots remain pending, and Couldn’t save identifies the affected capture with Retry save for the outstanding failures. Save failures have separate presentation state so they do not replace media/import/export errors. These are project-save states, distinct from export completion. The forced-failure native fixture passed; its scope and result are recorded in the validation log.
- **Workflows:** grouped sidebar choices participate in native Tab/Shift+Tab traversal and show a focus border. Enter/Space select the focused workflow and retain focus; selection alone does not execute capture or sharing steps. The native workflow fixture checks keyboard activation alongside pointer targets and layout boundaries.
- **Image properties:** the standalone editor uses the same selected-tool metadata as the overlay. Blur exposes strength, pixelation exposes block size, and the magnifier exposes zoom; text/font and shape-fill controls appear only for relevant annotation types. Effect controls do not require a context menu. The accepted-pixel/Undo native fixture and compact rendered panels have passed; exact results are recorded in the validation log. Selected text drafts remain attached to their annotation across selection changes, and unresolved or unobserved Apply results block output until reconciled.
- **Settings:** persisted capture quality, replay length, output folder, audio options and tray behavior sit alongside six editable global shortcuts. Shortcut registration status is visible; recording a replacement binding temporarily releases registered shortcuts and handles cancellation/focus loss. Microphone cleanup is chosen per saved replay and remains live; original full-recording microphone audio stays raw. The configured folder is displayed without filesystem resolution on every paint. Screenshot/workflow/sharing settings have an explicit route to Tools.

## Audio device selection rationale

Display identity is checked at startup, before the first captured frame, and around duplication recovery. These checks do not continuously verify physical identity through every possible topology change; display-change recovery still needs a real transition test. Unsupported color spaces are described as unsupported color modes, since they are not all HDR.

The Capture display selector enumerates monitors on one bounded read-only worker. Rows show resolution, GPU, Windows display name and actual unsupported reasons. **Windows primary display** is an explicit policy resolved fresh by the backend when capture starts, then pinned for that session; a primary monitor that cannot be captured fails explicitly instead of silently selecting another GPU/display. An explicit monitor uses its opaque display-device path. Missing selections remain unavailable until the user reconnects or chooses another; labels and list positions never substitute for identity. Capture and Settings disable display changes while a session starts, records or finishes. The active Capture label uses the immutable start-time preference: “Primary display at capture start” does not imply following later primary changes; “Configured at start” identifies a cached selection label rather than claiming newly verified physical metadata. The `capture-display-picker` owned-window fixture seeds only diagnostic monitors and exercises keyboard selection rejection, primary-policy selection, Tab containment and Escape without enumeration, capture, audio activation or preference writes.

Capture priority is a next-session choice. **Image quality** preserves the existing two-second keyframe interval and remains the migration/default value. **Editing speed** uses approximately half-second keyframes (ceil(FPS / 2), at least one frame), which can improve seeking in newly captured clips while reducing image detail at the same bitrate. Existing files and running capture sessions keep their current encoding. The controlled 1440p60 AV1 trials showed a real seek/detail tradeoff, not a guaranteed file-size increase; this option does not promise instant seeks or change the default. Choosing a priority persists through the existing preference acknowledgement; a failed save restores the previous selection.

Source failures retain their actual source-specific reason in Capture's Audio sources panel, including after stopping the session. The panel distinguishes active capture from finalization and the last stopped session; it does not claim an audio source recovered merely because video continues. The bounded scrollable details survive unrelated replay-save notices and clear when the next session resets its stats. During capture, guidance reminds the user to save needed replay before stopping to reselect a device. This follows the explicit device selection in [OBS Audio Sources](https://obsproject.com/kb/audio-sources) and the source/device troubleshooting in [SteelSeries Moments](https://support.steelseries.com/hc/en-us/articles/45991542004493-Quiet-Microphone-Volume-in-Moments-Clips). NVIDIA's [capture overview](https://www.nvidia.com/en-us/geforce/news/nvidia-app-download-and-features/) likewise separates rolling replay saves from full recordings; RCR does not imply that stopping automatically saves the current replay buffer.

The references support a small device selector alongside the existing source controls. [OBS's Device property](https://obsproject.com/kb/audio-sources) preserves a Default choice; [NVIDIA's overlay](https://www.nvidia.com/en-us/geforce/news/nvidia-app-download-and-features/) exposes sound-source settings and separate microphone tracks. [ShareX's implementation](https://github.com/ShareX/ShareX/blob/master/ShareX.ScreenCaptureLib/Forms/FFmpegOptionsForm.cs) refreshes its source list off the UI thread. RCR retains its separate Desktop/application source and microphone enablement, adding device choices without introducing scenes or changing the operating system's defaults.

Microsoft's [endpoint discovery example](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-properties) provides friendly labels and endpoint IDs; [loopback capture](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording) reads a rendering endpoint directly. IDs stay opaque: names are not unique, and ordinary IDs can change after driver or OS updates. RCR preserves an unavailable selection for explicit reselection. The newer optional [stable-ID property](https://learn.microsoft.com/en-us/windows/win32/coreaudio/pkey-audioendpoint-stableid) is not used by this increment. Unset selections preserve RCR's existing `eConsole` default role for both directions.

Read-only native discovery and explicit resolution have passed, alongside seeded picker input/state checks. These results do not establish recording through a selected microphone, permission/format compatibility or device-unplug recovery. Picker layout changes require their own rendered review; detailed results and pending checks remain in [VALIDATION.md](VALIDATION.md).

## Review boundaries

### Video preview acceleration

[OBS's media-source properties](https://obsproject.com/kb/media-sources) expose hardware decoding independently and document the reload cost of closing inactive media. [Medal's editor troubleshooting](https://support.medal.tv/support/solutions/articles/48001242234/) distinguishes app acceleration from recording acceleration and illustrates its advanced setting. RCR's design inference is to expose a plainly named **Use GPU video preview** option in Settings, keep recording independent, and preserve a working CPU fallback. Enabling an experimental decoder must not require editing shell variables or disabling the whole editor to recover. Changes apply to the next playback session; capture/encoding settings and project edits are separate. The conservative default remains off while broader source and presentation coverage is developed. Automatic runtime discovery, unsupported-source rejection before device creation, and the Settings-equivalent 360-frame GPU preview have passed native proofs; these do not establish every source/device combination or uniform monitor pacing.

Application-audio backend proofs used controlled quiet tones on Windows build 26200.9711, without recording desktop video, microphone audio or PCM files. Selected-process isolation, parent/child inclusion, stale-fingerprint rejection and target-exit reporting have run; the evidence and measured limits belong in [VALIDATION.md](VALIDATION.md). The optional `scripts/verify-process-audio.ps1` uses FFplay tone generators, supports `-IncludeChildren` and `-ExpectExit`, and retains only JSON/text evidence. This does not establish compatibility with every game, protected audio path or device transition. Microsoft's [process activation parameters](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ns-audioclientactivationparams-audioclient_activation_params) list build 20348, while the [activation function](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync) currently says 20438; runtime activation errors remain authoritative, and general Windows 10 support is not claimed.

The implementation descriptions above are based on source inspection. Newly added tests and native fixtures are verification mechanisms, not proof of a successful run. See the dated validation record for completed results. Hidden native fixtures exercise the app's own GPUI layout, paint and input dispatch; explicit UI render fixtures capture only its owned render target with Computer Use disabled. They do not inspect or operate the desktop. This document makes no claim of pixel-perfect reproduction, screen-reader coverage, mixed-DPI/HDR interaction, long-running capture reliability or competitive latency against the referenced apps. RCR remains a Windows/NVIDIA/SDR-first product with the platform and media constraints documented in the repository.

Export details now keeps incomplete-file recovery beside its diagnostic explanation. Its body scrolls while the heading and Close stay visible; keyboard traversal skips actions already running. On Windows, diagnostic text uses a bounded worker and the current GPUI window's clipboard owner. Copying becomes Copied only after the actual transfer and close acknowledgement, with failure available for retry inside the panel. Closing or switching captures cannot apply an old result to another diagnostic. The non-Windows clipboard API does not provide that acknowledgement, so its label says Copy requested. Native validation results are recorded separately.

### Region section marking

The region tool previews detectable native window/control bounds under the pointer, such as a Win32 application pane. Hover bounds remain separate from the committed capture region. A click adopts the candidate without copying or saving; dragging beyond the small click threshold draws a free rectangle from the press point instead. Once committed, the existing region's handles and move gesture take priority over target detection. Release retains an adjustable region; Copy/Save or canvas Enter explicitly completes the action. Annotation tools do not adopt hovered targets.

The candidate/selection has a contrasting black-and-white dashed outline, physical screen X/Y coordinates and width/height. A pointer magnifier uses an 11×11 sample from the annotation Surface's existing BGRA tiles, with no additional full `Frame` copy. Its panel flips/clamps at the capture boundary. Guides, coordinates and magnifier remain presentation-only and are absent from copied/saved pixels. Existing Shift-square creation and Shift-arrow region resizing remain available; these are RCR's shortcuts, not a claim to duplicate ShareX's cursor shortcuts.

Detection runs once on a background worker before opening the overlay, using a physical-coordinate HWND rectangle snapshot. It is bounded by 2,048 targets, 4,096 visited handles, depth eight, a 50 ms budget checked between OS calls and one concurrent snapshot. The budget cannot preempt an individual OS call. Hover performs only immutable geometry lookup; it sends no application messages and does no OS or accessibility queries. Native HWND children can identify many desktop panes, but windowless web/custom-drawn subregions are not semantic targets. No UI Automation detector or arbitrary visual-pane recognition is implied; manual rectangle drawing remains available when no useful candidate exists.

The primary behavioral references are ShareX's [native window/control enumeration](https://github.com/ShareX/ShareX/blob/develop/ShareX.ScreenCaptureLib/Helpers/WindowsRectangleList.cs), [separate hover/selection interaction](https://github.com/ShareX/ShareX/blob/develop/ShareX.ScreenCaptureLib/Presentation/RegionCapture/RegionCaptureWindow.axaml.cs), and [event-driven region outline](https://github.com/ShareX/ShareX/blob/develop/ShareX.ScreenCaptureLib/Presentation/RegionCapture/RegionSelectionOverlay.cs). RCR keeps explicit confirmation, corresponding to ShareX's [adjustable selection workflow with Quick capture disabled](https://getsharex.com/docs/region-capture). These sources inform the interaction contract; implementation validation and remaining native coverage belong in [VALIDATION.md](VALIDATION.md).

### Recovery and responsive completion

Screenshot overlays retain the same frozen image and editable annotations until the chosen action reports success. Copy/save failures leave the toolbar and error visible for retry; a configured workflow is not rerun when doing local recovery. Escape first dismisses temporary help, an active gesture or annotation selection before cancelling the entire capture. These actions follow the staged editing behavior described by the official ShareX region guide.

The standalone editor retains successful local steps across identical-pixel retries: a saved image is not saved again solely because clipboard copy failed. Editing pixels starts a new output while preserving any prior successful save. Clipboard admission is bounded to one operation, and callbacks from older sessions cannot replace current status. Completion uses the existing bounded UI wake channels rather than a perpetual completion polling loop. Library work is cancelled by catalog revision; stale thumbnails cannot replace the current catalog, and catalog queue admission no longer runs on every paint. Actual native evidence and remaining cancellation limits are recorded in VALIDATION.md.
